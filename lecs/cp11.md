# 11. Network Programming

## 11.1 The client-sever programming model

- client-server 모델이란? 어플리케이션이 하나의 서버 프로세스와 여러개 클라이언트 프로세스로 구성된 상황.
  - 서버가 디스크 파일을 클라이언트 대신 실행해주고 검색(retrieve)해주는 역할을 수행함.
- 클라이언트-서버 모델의 기초 동작(fundamental operation)은 트랜잭선이라고 불리며 아래 네 단계의 스텝으로 구성됨  
  - 먼저 클라이언트가 서비스가 필요하면 요청을 보내는 식으로 트랜잭션을 시작한다. 예를 들면 웹브라우저가 파일이 필요할 때 서버에 요청하는 식.
  - 서버는 요청을 받고, 해석하고, 그에 대응되는 행동을 한다. 예컨대 받은 요청에 대한 디스크 파일을 읽는다던지.
  - 이후 서버는 응답을 보내고, 대기한다.
  - 클라이언트는 서버의 응답을 받고, 요청된 걸 만진다.
- 하나 중요한 건, 서버 / 클라이언트는 호스트 / 머신이 아니라 프로세스 단위에서 생각되어진다는 것.

## 11.2 Networks

- 네트워크란 뭘까? usage를 통해 생각해보자면, 분리된 호스트들끼리 통신하기위해 사용하는 하드웨어 / 소프트웨어 자원 중 하나를 일컫는 것.
- host 관점에서 보면 네트워크는 그냥 "또다른 io device"다. io 버스에 네트워크 어답터가 붙어 있다.
  - 이 어댑터를 통해서 외부로 오는 데이터를 복사해서 메모리로 가져오거나 그 반대방향을 수행하거나 한다. 통상 DMA transfer를 수행.
- LAN이란? 네트워크의 종류 중 하나로, 정말 물리적으로 빌딩 같은 곳에 있음. 좁은 지역을 연결하는 기술. LAN의 가장 대표적인 기술이 이더넷임.
  - 이더넷 세그먼트는 wire와 hub로 구성되어있고, wire의 한 쪽은 머신의 네트워크 어답터에 한쪽은 허브의 포트에 붙어있는 방식으로 연결.
- 이더넷 어답터(=네트워크 어답터)는 48비트 주소를 가지고, 다른 곳으로 정보를 보내기위해 "프레임"을 사용한다.
  - 프레임은 header와 payload로 구성되어있고, header는 도착주소와 사이즈 등 여러 정보를 가지고 있음.
- bridged ethernet이란 여러개의 이더넷 세그멘트를 하나의 LAN에 연결한 형태임.
  - 이더넷 세그먼트(ethernet segment)란? 여러개의 host가 하나의 허브로 연결된 형태.
  - bridge: 몇개의 wire와 small boxes로 구성된 것. 이걸 사용하면 hub보다 wire가 더 좋을 때 wire의 bandwidth를 더 잘 사용할 수 있음.  
- Q. 호환되지 않는 LAN을 연결하려면 뭐가 필요한가? A. 라우터.
  - 각 라우터는 포트(port, 그리고 어댑터)를 가지고 있고 이걸로 연결한다.
  - 라우터는 WAN(wide area network)를 만들어내고 이게 LAN을 연결함으로써 가능한 것임.

### 프로토콜

- Q. LAN 사이에서도, WAN에서도 기술상 불일치가 굉장히 클 수 있는데, 이러한 불일치 속에서도 어떻게 통신이 가능하도록 만들 건가?
  - A. 프로토콜 소프트웨어(Protocol Software)로. 크게 두 가지가 존재함.
    - Naming Scheme: host address에 대한 단일화된 형태 제공. 각 호스트는 자신을 인식할 수 있는 internet address를 부여받게 됨.
    - Delivery Mechanism: 보내는 데이터의 구조를 통일. 패킷이라고 하고, 헤더와 페이로드로 구성.
- LAN1에 속한 호스트 A가 LAN2에 속한 호스트 B로 보내는 상황을 가정해보자. 크게 8단계로 구성.
  - A의 머신에서 syscall을 통해 virtual address에 있는 데이터를 kernel buffer로 옮겨두고,
  - A의 머신에서 protocol software가 동작해서 L1 frame을 만든다. L1 frame은 l1 headerd와 ip packet으로 구성된다. ip packet은 ip packet의 헤더와 payload로 나누어진다. frame의 header는 향후 임시로 방문해야할 라우터에 대한 정보(주소)를 가지고 있고, ip packet의 헤더는 실제로 동작할 host B의 주소가 있다. 이걸 ph(packet header), fh(frame header)와 같은 말로 구분함.
  - host machine 어댑터가 프레임을 네트워크에 복사한다.
  - 라우터 네트워크 어댑터가 와이어를 통해서 읽고, protocol software에 프레임을 보낸다.
  - protocol이 desination address를 index로 routing table을 조회한다. 향후 어디로 보내야할지 결정하고, 프레임의 헤더를 변경하여 포워딩.
  - 복사하여 다음 라우터로 전송.
  - LAN2의 라우터가 받고 프로토콜을 통해 프레임을 재변경.
  - host b가 받고 virtual space에 복사해둔 다음, syscall을 통해서 읽는 작업을 수행한다.

## Global IP internt

- 프로토콜에는 여러가지 종류가 있다. 예를 들어,
  - IP: 가장 기초적인 형태의 naming scheme과 delivery mechanism을 제공한다. packet은 datagram이라는 형태임. host에서 host로 전달한다. 유실됐을 때 복구하는 절차가 없다는 점에서 unreliable한 프로토콜임.
  - UDP: IP를 조금 개선한 형태로, host to host가 아닌, process to process를 수행한다.
  - TCP/IP: 모던 시스템이 사용하는 프로토콜. IP 위에서 개발되었으되 reliable하게 만든 형태.
- host들은 32bit 주소로 표현(매핑)되고 이걸 IP라고 함.
- IP address들은 Internet Domain Names로 매핑된다.
- 사람이 알아보기 쉽게 점을 붙여서 만든 버전(e.g., 8.8.8.8)이 있고 실제 비트버전이 있다. 점(dot)이 붙은 버전은 presentation용이고, 실제 네트워크에서는 수로 쓴다.

### Internet Domain Names

- 통신을 위해 ip를 외워야하면 쉽지 않을 것. 그래서 사람들이 domain names라는 걸 만들고 그걸 ip랑 매핑시킴.
  - 우리가 잘 아는 형태로 cs.cmu.edu와 같은 형태임.
- domain names는 일종의 계층이 있다.
  - 맨 첫 번째 층은 root로 시작지점이며 그 자체로 가지는 의미는 없다.
  - 그 다음 층은 도메인의 뒤에서부터 시작한다. 예제로는 edu가 여기에 속한다.
  - 그 다음 층은 cmu로 edu의 서브도메인에 해당한다. 중요한 정보일수록 뒤에 위치하고 앞으로 가면 뒤의 서브도메인이 된다.
- 그럼 이런 매핑은 어떻게 관리될까? DNS(Domain Name Space)라는 형태로, 전 세계적으로 관리된다.
- localhost란? 네트워크에 연결된 host가 자기 자신 안에서 "locally defined"된 형태로, 127.0.0.1을 의미한다.
  - host가 자기자신에게 연결하는 형태라고 생각하면 됨. 프로세스에 내부에서 보는 게 아니고, 자가자신을 네트워크를 통해 보는 형태.  

### Internet Connection

- 서버와 클라이언트는 연결(connection)을 통해 데이터를 주고 받는다. 이때 full duplex하다고 표현하는데, 양방향으로 흐를 수 있고 신뢰할만하다는 의미.
- 이 연결의 끝을 소켓(socket)이라고 부른다. 소켓은 그에 대응하는 주소를 가지고 있는데, 이게 ip address + port(16bit) 넘버임.
  - 각 서비스마다 전형적인 포트넘버들이 있다. 웹서비스는 80, 이메일은 25와 같은 식.
- 이러한 이유로 연결을 (cliaddr:cliport, servaddr:servport)와 같은 형태로 표현할 수 있다. 소켓 주소만 있으면 되니까.

## 소켓 인터페이스

### Socket Address Structures

- 소켓 주소(address)는 sockaddr_in이라는 16바이트 공간에 저장되어있음. 구성요소를 살펴보자면,
  - sin_family는 AF_INET으로 설정되어있고(Q. AF_INET이 뭔가?)
  - 포트넘버는 sin_port에, ip 주소는 sin_addr에 저장되어있음. 빅엔디안으로 저장되어있다.
- Q. 여러 프로토콜이 존재하는데 통신에 사용되는 함수(bind, connect, accept)를 어떻게 구현할까?
  - A. sockaddr이라는 범용 구조체로. 이때 어떤 프로토콜의 구조체든 해당 함수들에는 sockaddr 포인터로 캐스팅되도록 해야한다.
- 구체적인 예제를 보자면,

```c
/* IP socket address structure */
struct sockaddr_in {
uint16_t sin_family; /* Protocol family (always AF_INET) */
uint16_t sin_port; /* Port number in network byte order */
struct in_addr sin_addr; /* IP address in network byte order */
unsigned char sin_zero[8]; /* Pad to sizeof(struct sockaddr) */
};
/* Generic socket address structure (for connect, bind, and accept) */
struct sockaddr {
uint16_t sa_family; /* Protocol family */
char sa_data[14]; /* Address data */
};
```

- sockaddr_in은 특정 프로토콜에 대한 정의이지만, 다른 프로토콜에서는 다를 수 있다. 이러한 이유로 해당 프로토콜 구조체의 포인터를 sockaddr의 포인터로 캐스팅한다.
- 이러한 사실을 감안하면 모든 프로토콜은 최소한 위와 같은 sockaddr 캐스팅에 문제가 없어야 한다.  

### The socket function

- socker 함수는 소켓 descriptor를 만든다. 연결의 종단점에 해당하는 소켓을 만들려면 `clientfd = Socket(AF_INET, SOCK_STREAM, 0);`와 같이 사용하면 된다.
  - AF_INET은 32비트 ip 주소를 사용한다는 의미이며, SOCK_STREAM은 연결의 end point임을 의미한다.
- 해당 함수는 부분적으로 열린(partially open) 형태의 socket descriptor를 제공한다. 따라서 아직 읽고 쓰는 건 불가능.

### connect function

```c
#include <sys/socket.h>
int connect(int clientfd, const struct sockaddr *addr,
socklen_t addrlen);
```

- clientfd는 descriptor(Handle), sockaddr 안에 있는 ip 주소와 port number가 서버에 클라이언트 주소로 등록된다.
- connect 단계가 성공적으로 끝날 때까지는 잠시 블라킹이 된다.
- 성공적으로 마무리가 되면 비로소 reading과 writing이 가능한 상태가 됨.

### bind, listen, accept function

- 세 함수 모두 클라이언트와의 연결을 위해서 "서버"가 사용하는 함수들임.
- 먼저 bind를 살펴보자면,

```c
#include <sys/socket.h>
int bind(int sockfd, const struct sockaddr *addr,
socklen_t addrlen
```

- bind라는 이름처럼 sockfd와 그것의 주소를 결부시키는 작업으로 볼 수 있음. bind 함수가 커널에게 해당 매핑을 요청하는 식.
  - 하나 짚고 넘어가자면 "서버"는 머신이 아니라 프로세스다. 그렇기 때문에 동일 머신 안에서 벌어지는 일임에도 "커널"을 서버와 분리해서 생각하는 것.

```c
#include <sys/socket.h>
int listen(int sockfd, int backlog);
```

- 클라이언트는 요청을 하는 active한 애들이고, 서버는 요청을 받아들이는 수동적인 존재들임.
  - 근데 소켓이 만들어질 때를 생각해보자. 이걸 "서버"용으로 만들었는지 "클라이언트"용으로 만들었는지 알 수 없다.
  - socket으로 만들고, bind로 연결은 했는데, 이제 무얼 해야하는가?
- A. 서버라면 listen. "나는 액티브하게 연결하려는 용도가 아니고", "클라이언의 연결 요청을 기다리는 용도"다라는 내용을 커널에 알림.
  - 즉, 서버는 머신에서 kernel을 통해서 통신을 관리함.
- 이 과정을 통해 해당 socket(sockfd에 대응되는)은 active에서 listening으로 상태가 변경됨.

```c
#include <sys/socket.h>
int accept(int listenfd, struct sockaddr *addr, int *addrlen);
```

- 서버는 위와 같은 accept 함수를 통해서 클라이언트로부터의 연결요청을 기다린다.
- 먼저 서버는 listenfd에 클라이언트로부터 요청이 오기를 기다린다. addr에 소켓 주소를 기록하고 "conneted descriptor"를 리턴한다.
- 아주 당연한 질문. listenfd와 connectedfd(이하 connfd)가 나누어져야 하는 이유가 무엇인가? 책은 두 개를 아래와 같이 분리한다.
  - listenfd: 클라이언트 연결 요청의 엔드포인트에 위치한 디스크립터. 한 번 생기면 서버의 라이프타임동안 존재한다.
  - connfd: 서버와 클라이언트 연결 자체의 엔드포인트에 위치한 디스크립터. 클라이언트에게 서빙하는동안만 존재함.
- connfd와 클라이언트쪽의 clientfd를 통해 서버와 클라이언트는 통신한다. 각각의 디스크립터에 write하는 방식.

### host and service conversion

```c
#include <sys/types.h>
#include <sys/socket.h>
#include <netdb.h>
int getaddrinfo(const char *host, const char *service,

Returns: 0 if OK, nonzero error code on error

void freeaddrinfo(struct addrinfo *result);

```

  - 현재 매우 액티브하게 사용되는 함수. 호스트 주소 / 서비스 이름 / 포트 넘버 등을 만들어 구조체로 만들어 줌.

### 소켓 인터페이스를 위한 헬퍼 함수들

- open_clientfd, open_listenfd 함수는 서버 / 클라이언트가 상호 소통하고 싶을 때 사용하는 함수임.
-
