# 10. System level I/O

- i/o(input/output)란 어떻게 정의할 수 있을까? 우리는 "디바이스와 메인메모리 간 복사를 수행하는 프로세스"라고 생각할 수 있다.
  - input은 device에서 main memory로 가는 복사, output은 main memory에서 device로 가는 복사를 의미.
- 일반적으로 io는 언어레벨(c의 scanf / printf)에서 지원하기도 하고, os에서 높은 수준의 함수(linux의 unix i/o wrapping)를 제공해주기도 한다. 그런데 왜 우리는 unix의 system level i/o를 배워야할까?
  - i/o 자체가 의존성을 만드는 경우가 있을 때, i/o에 대한 깊은 이해가 필요해진다.
  - system level i/o 아니고서는 답이 없는 경우들이 존재한다.

### 주의사항

- unix에서 말하는 "everything is a file"에서의 file은 정말 파일시스템에서 다루는(=이름이 있고, 데이터가 바이트 시퀀스 형태로 존재하는) 파일이 아니다.
- read/write/open/close 같은 인터페이스로 다루는 I/O 대상을 파일로 본다. regular file하고 같은 점은 "동일 인터페이스로 다루어진다" 밖에 없음. 실제로 데이터가 물리공간 안에 저장되는 형태도 아님.

## 10.1 Unix I/O

- 귀납적으로 정의해보자. 리눅스 파일은 바이트의 시퀀스이다.
- 그리고 모든 io 디바이스들은 파일에 매핑시킬 수 있다. 이 방법은 커널이 디바이스에게 신호 보내는 걸 쉽게 만들어준다. 구체적인 동작들을 살펴보자면,
  - 파일 열기: application은 파일을 엶으로써 디바이스에게 "접근한다"는 신호를 보낸다. 이때 커널이 descriptor라는 작은 양수값을 전달해준다. 리눅스 쉘을 통해 실행되는 모든 프로세스는 세 개의 파일(standard input / output / error)을 열면서 시작한다.  
    - fd(file descriptor)가 뭔가? 커널이 파일을 열어두었을 때, 파일에 접근하도록 만들어주는 일종의 핸들이다. 그 핸들의 값이 작은 양수 형태라고 생각하면 된다.
  - 현재 파일 포지션 변경: 커널은 항상 파일 포지션을 기록해둔다. 0부터 시작하고, 시작부터 현재 위치까지의 byte offset k가 현재 파일포지션임. application은 seek operation으로 file position을 정한다.
    - application은 여기서 실행중인 사용자 프로그램으로 이해하면 된다.
    - 여기서 "k만큼 읽는다"를 vim 같은 프로그램에서 커서 위치가 k에 위치에 있다고 생각하면 안 된다. c/c++에서 syscall read를 호출하는 걸 생각해야한다(read(fd, buf, n);)
  - 읽고 쓰기: 읽기는 파일에서 메모리로 복사하는 것이다. 이때 offset k가 실제 파일 크기보다 크면 EOF 만남. 쓰기도 반대방향으로 마찬가지 메인메모리를 파일로 복사한다.
  - 파일 닫기: 닫을 때 되면 커널에 요청해서 닫는다. 파일을 열어두었던 프로세스가 끝나면 모든 열린 파일들은 닫히게 된다.  

## 10.2 Files

- 여러가지 종류의 파일들이 존재하지만, 크게 세 가지를 다룬다.
- regular file: 우리가 생각하는 일반적인 형태의 그 파일이다. text / binary로 나누어서 생각할 수 있다. text는 line의 시퀀스이고, 개행문자에 의해 시퀀스가 나누어진다고 생각할 수 있다. 바이너리는 바이트만 존재하는 형태고.
- directory: 링크의 배열(array of links). 파일 이름과 파일을 이어주는 링킹을 수행
- socket: 네트워크에서 다른 프로세스와 통신하기위해 사용되는 파일.

## Short count

- short count란? read / write가 실제로 요청된 것보다 더 적은 양의 데이터를 전달하는 경우.
- 왜 발생하는가?
  - EOF를 만나는 경우: 당연히 EOF보고 종료.
  - 터미널을 읽어오는 경우: 터미널에 작성된 텍스트의 양을 예측할 수가 없고, "터미널에 입력된 양만큼 읽는" 경우에는 short count 발생.
  - 네트워크 소켓을 다루는 경우: 내부 버퍼링이나 네트워크 딜레이가 short count를 만드는 경우.
- 이 자체는 에러가 아니고 정상동작이다. 다만 사용자 입장에서 "x를 요청했지만 실제로는 y만큼 오는 경우"에 대해 충분히 대비할 수 있어야 한다.

## 10.5 Robust reading and writing

- short count에서 발생하는 동작을 잘 대비해보자. rio(robust i/o)라는 컨셉의 프로그램을 만들기 위해 크게 두 가지 기능을 제공할 예정.
  - unbuffered i/o 함수들: application buffering 없이 메모리 <-> 파일간 전송을 수행하는 방법.
    - Q. application buffering이 정확히 무엇이고 왜 병목현상이 되는지에 대한 규명 필요.
    - A. 진짜 별거 아니고, 해당 함수에 별도의 버퍼 없이 인자로 들어온 포인터를 기준으로 데이터를 저장한다. 그래서 non-buffer임. 그 이상 그 이하도 아니다.
  - buffered input 함수들: application buffer에 캐시된 내용을 효과적으로 사용하는 것이 목표임. thread-safe해서, 임의의 위치에 위치시키는 것(arbitary interleaving)이 가능하도록 만들어야.
