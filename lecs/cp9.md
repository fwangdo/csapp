# 9. Virtual memory

- Q. 가상 메모리는 왜 필요한가? A. 다양한 프로세스마다 고유의 메모리가 필요하다면 너무나 큰 메모리가 필요하고, 쉽게 corrupted 되기 때문.
- 가상 메모리가 주는 세 개의 능력(capabilities).
  - 1. 메인 메모리를 디스크에 대한 일종의 캐시로 사용하도록 하는 역할을 하고,
  - 1. 단일한 규칙의 메모리 주소를 여러 프로스세스에 공급하여 메모리 관리를 쉽게하며,
  - 1. 다른 프로세스에 의해 특정 프로세스의 메모리가 오염되는 것을 막음.

## 9.1. 물리 / 가상 주소

- 물리 주소(physicall adressing): M개의 바이트조각이 연속적으로 나열된 형태.
  - load 명령을 받으면? 메인 메모리에서 요구된 위치에서 그만큼의 메모리를 받아 cpu에게 돌려줌.
- 가상 주소(virtual addressing)
  - cpu가 메인메모리에 접근할 때 가상주소를 생성여 접근함. 보내지기 전에 물리 주소로 변경되고 이걸 주소번역(address translation)이라고 함.
  - cpu에는 memory management unit(MMU)라는 게 존재하고 이게 가상주소를 번역해줌. 번역 정보는 메모리 안에 page table 형태로 존재하고 os가 이걸 관리함.
  - 번역방향은 virtual to physical임.

## 9.2 주소 공간

- n비트 공간이 있으면 주소 공간은 당연히 [0, 2^-1] 같은 꼴을 생각할 수 있음.
- 여기서 메모리 주소가 몇 비트로 표현되느냐에 따라 특징지어줄 수 있음(e.g., 32-bit, 64-bit..)
- 중요한 특징은, 저장되는 값인 data bytes와 그 속성인 주소를 구분할 필요가 있다는 것임.
  - 하나의 데이터에 대해 두개의 주소를 가질 수 있음. 그래서 물리 주소, 가상 주소가 동시에 하나의 데이터를 가리킬 수 있는 것.

## 9.3 캐싱관점에서의 VM

- 가상 메모리(VM)은 N 바이트가 연속되는 배열이라고 볼 수 있고, 해당 주소가 virtual address임. 즉, virtual address -> data 매핑이 성립한다.
  - 단, 정말 데이터가 저장되는 것은 아니고, "논리적으로는 매핑이 가능하다"임. 실제 물리적으로 저장되는 곳은 다른 곳이다.
- 이 주소의 "컨텐츠"들은 메인 메모리에 캐싱된다. 이때 더 아래 계층(e.g., disk)는 블록으로 쪼개지고 이 중 일부를 윗계층(e.g., 메모리)으로 전송하기 위한 전송유닛으로 사용한다.
  - 이런 형태의 쪼개진 블락을 VM은 virtual page라고 칭하고, 피지컬 메모리 계층에서는 physical page라고 칭함.
  - 따라서 vp와 pp는 "메모리 공간"에 대한 매핑으로 볼 수 있음.
- 가상 페이지들은 세 가지 상태로 구분할 수 있다.
  - unallocated: vm에 의해 할당되지 않은 영역. 아무런 데이터도 없음.
  - cached: 현재 피지컬 메모리에 할당된 영역
  - uncached: 현재 피지컬 메모리에 할당되지 않은 영역.
  - Q. 가상 페이지와 피지멀 페이지가 서로 대응관계에 있는데, 가상에는 있으나 피지컬에는 없다는 게(uncached) 무슨 말인가?
  - A. VM상에서 페이지가 할당되었는데, pp에 데이터가 없는 경우임. 예를 들어 VP에 데이터가 있었고 PP에서 캐시했는데 PP가 evicted되면 이런 상태일 것.
  - Q. VP가 PP를 캐싱하는 게 아니고, PP가 VP를 캐싱하는 게 맞나? 방향이 반대 아닌가?
  - A. 반대 아니다. PP가 VP를 캐싱한다. VP가 논리적 기준이 되는 페이지고, PP 일종의 캐시 슬랏이다.
- 정리하자면,
  - VP <-> PP는 메모리 공간에 대한 매핑이다.
  - VM이 VP를 할당하고, 이에 따라 VP / PP 간에 세 가지 상태가 존재할 수 있다. 이 셋을 가르는 핵심 키워드는 할당되었는가 & 데이터가 존재하는가 이다.

### 9.3.1 DRAM cache organization

- 지금까지 언급한 virtual page가 있는 캐시를 DRAM-cache라고 부르고, SRAM용 캐시는 SRAM-cache로 부른다.
- 캐시미스가 날 때, SRAM보단 DRAM에서 일어나는 게 더 타격이 크다. DRAM에서 가져오는 것보단 disk에서 가져오는 게 훨씬 느리기 때문.
- 따라서 DRAM에서는 최대한 캐시 미스를 피해야하고 이런 이유로 임의의 PP를 VP가 사용할 수 있도록 하는 구조를 만듦. 이걸 fully associative하다고 함.
  - Q. VP의 특성인 페이지 단위 관리를 고려해보면 당연한 것 같은데 왜 대단한 것처럼 말하나?
    - A. 캐시를 생각해보면 다름. 캐시는 일종의 해시라서 공간이 더 남아있더라도 해시값이 다르면 저장 못할 수도 있음. 사실상 캐시와 메모리간 매핑이 있는 것.
    - 반면 가상 페이지는 완전히 논리적으로 운영되기에 그런 문제로부터 자유로움.

### 동작과정

- 가상 <-> 물리 매핑은 os를 통해 이루어지며, 하드웨어상에서는 mmu라고 하는 부품을 통해 수행된다.
- 또한 os 안에서 가상 메모리 -> 물리 메모리 매핑이 있고 이걸 page table라고 한다.
- page table entries를 보자. set / address field로 나누어져있고, set이 1이면 해당 가상 메모리 주소에 대응되는 PP가 DRAM에 올라왔다는 뜻.
  - 반대로 0이면 현재 캐싱되지 않았다는 뜻. 이때는 address field가 null일 수도 있고, disk를 가리킬 수도 있음.
  - Q. 물리주소는 아는데 가상주소는 어떻게 아는가? A. 인덱스 값이 VP의 주소라고 생각하면 된다. PTE[1]이면 1번 VP에 대한 정보라는 식.

### 정리해보자면

- VP는 일종의 "논리적 정체성(identity)"이다. 프로세스 입장에서는 "여기에 데이터가 있다"고 생각하고 접근한다.
- 그렇다면 그 주소에 정말 데이터가 있는가? 그렇지 않다. 다른 물리 메모리에 존재한다.
- 그럼 어떻게 찾아가는가? MME를 사용해서 PTE로 간다. 거기서 valid bit이 1이면 DRAM 안에 있는 거고, 그렇지 않으면 uncached거나, 아니면 valid하지 않거나.
- 즉 VP는 가상으로 별도의, 구분되는 메모리 영역을 만든 것이고, 거기서 "내가 관심이 있는 메모리가 어느 영역에 있든 추상화해서 사용할거다"는 생각으로 만들어진 거다. "실제 데이터가 어디에 있고 어떤 상태인가?"는 PTE를 통해서 관리된다.

### page hit and fault

- page도 일종의 cache이므로 hit과 miss(fault)가 있다. hit은 VP를 봤을 때 valid bit이 1이면 자명히 가져올 수 있음.
- 만약 valid bit이 0이다? 마찬가지로 victim page를 가져와야함. 이때 일어나는 일은 캐시와 상당히 유사하다 victim을 disk에 다시 쓰고, 가져올 건 ram으로 올리고.
- `demand paging`이라는 표현이 있는데, 메모리가 실제로 필요할 때까지 기다렸다가, 필요해지면 그때서야 올리는 lazy한 방법을 의미한다. 현대 시스템에서는 이게 대세.

## 9.4. 메모리 관리도구로서의 가상 메모리

- 지금까지는 하나의 PTE만 생각했지만, 사실은 여러개의 PTE가 동시에 존재할 수 있고, 각 프로세스는 각각의 PTE를 가질 수 있다. 다시 말하자면, 각각의 프로세스는 각각의 가상 메모리 주소를 가질 수 있고 이것들은 큰 장점을 준다.
  1. 링킹에 큰 장점을 준다. 피지컬 메모리 주소를 알 필요 없이, 동일한 메모리 규칙을 적용할 수 있다. 예컨대 0x40번지에서는 특정코드만 와야한다거나.
  2. 로딩도 마찬가지. text와 data가 어디에 있는지 쉽게 파악할 수 있고.
  3. 공유: 여러개의 프로세스에서 c의 스탠다드 라이브러리를 사용하는 상황을 가정해보자. 실제로는 하나의 PP에 있지만 여러개의 VP에서 한 곳을 지칭하는 것이 가능하고, 그러므로 메모리 낭비 줄일 수 있음.
  4. 쉬운 메모리 할당: 큰 배열을 생각해보자. 물리 메모리라면 거기에 꼭 맞는 공간을 찾아야하지만, 가상 메모리에서는 적당히 짤라서 쓸 수도.

## 9.5 메모리 보호도구로서의 가상 메모리

- 가상 메모리는 메모리 구획을 나눈다는 점에서도 보안성을 높이지만, PTE를 통해 더욱 강력한 메모리 보호 방법을 제공하기도 함.
- 방법은 sup / write / read bit도 추가하는 것.
  - sup bit이 1이면 커널모드만 접근 가능함. 유저모드로 실행중인 프로세스는 접근 불가능.
  - write / read도 마찬가지. 1인 경우에만 쓰고 읽는 게 가능.
  - 허가되지 않은 종류의 행동을 하게 되면 segmentation fault가 발생함. 핸들러가 sigsegv를 수행하는 방식으로 처리.

## 9.6 주소 번역(address translation)

- 먼저 VAS와 PAS를 정의하자. VAS는 virtual address space, PAS는 physical adress space를 의미한다.
  - 매핑 함수는 가상주소 A를 넣었을 때, 그게 피지컬 주소 영역에 있으면 그에 대응되는 주소를, 그렇지 않으면 공집합을 반환한다.
- cpu가 mmu를 통해 매핑을 수행하는 과정을 생각해보자. 해당 작업에는 PTBR(page table base register)라는 전용 레지스터가 사용된다.
  - 가상 주소가 n비트라고 할 때, 이건 크게 두 개로 나누어진다. 페이지 넘버를 의미하는 VPN과, 페이지 내 데이터의 위치를 이야기하는 VPO(offset)이 그것.
  - 물리주소도 마찬가지 크게 두 개로 나누어지고, 넘버는 PPN, 위치는 PPO로 불린다.
  - PRBR이 현재 page table을 가리고 있을 때, 적당한 vp index가 들어온다고 가정해보자.
    - VPN은 바로 알 수 있다. 따라서 그에 대응되는 PPN은 바로 알 수 있고, VPO와 PPO는 "사실상 동일"하다. 즉 인덱스를 통해 가상 페이지 주소를 찾고, 그에 대응되는 피지컬 페이지 매핑을 얻고, VPO를 그대로 사용하면 원하는 메모리에 접근할 수 있다는 것.

### page hit

- 다음 다섯 단계를 거침.
- 프로세서(cpu)가 가상주소를 만들고 mmu에 보냄.
- mmu가 pte address를 만들고 cache/main memory에 요청을 보냄.
  - pte address를 만든다는 게 무슨 뜻인가? 정보를 찾는 입장에서는 pte가 필요한데, 그게 어디있는지 모르니 mmu가 pte 주소를 찾는(계산하는) 과정을 의미함.
- cache/main memory는 pte를 만들고 리턴.
  - 정확히 말하면 만든다기보단, 이미 존재하는 PTE를 읽어서 가져옴.
- mmu는 물리주소를 만들고 다시 cache/memory 쪽으로 보냄.
  - 물리주소를 만든다는 것은 가져온 PTE를 기반으로 PPN / PPO를 확보한다는 것.
- cache/main memeory가 요청된 자료를 프로세서에게 전송.

### page fault

- 이건 스텝이 7단계임. 1-3은 동일한데, "못 찾은 상황"을 가정해보자.
- step4. 확인해보니 PTE의 valid bit이 0임. MMU가 예외를 발생시키고 os의 예외 처리기가 반응함.
- step5. fault handler가 희생자 페이지(victim page)를 찾고, 변경된 페이지는 disk out된다.
- step6. fault handler가 PTE를 업데이트한다. 대응되는 PPN / PPO를 쓰고.
- step7. 실패한 명령어로부터 재실행한다. 이때부턴 page hit의 논리를 그대로 따라가면 됨.

### Table lookahead buffer

- pte를 l1 cache에서 가져오려면 n cycle이 드는데, 이것도 줄이고 싶고, 이렇게 등장한 개념이 TLB임.
- tlb는 index와 tag, 그리고 vpo로 구성되어있는 캐시이고, index와 tag를 통해 set selection을 수행한다. single line cache라 set selection 만으로 값은 획득할 수 있고, vpo는 pa를 계산하기위해 쓰인다.
- 순서는 cpu가 가상주소 만들면 -> mmu가 tlb에서 pte 가지고오고 -> pte에서 가상주소 번역한 다음 캐시나 메모리에 피지컬 주소로 저장된 값 요청하고 -> 프로세서(cpu)가 값 획득하고.

### 부록. 사이즈 계산하기

- 먼저 B(바이트), KB, MB, GB 간의 관계를 규명해보자. 첫 스텝은 바이트의 크기를 정의하는 것이다. 1B = 8bit.
- 1KB = 1024B(엄밀히는 1000B지만 power of 2로 통일.), 1MB = 1024KB, 1GB = 1024MB
- 즉, KB = 2^10B, MB = 2^20B, GB = 2^30B

### multi level page table

- 32비트 주소를 사용하는 경우를 생각해보자. 한 페이지가 4KB를 가진다고 가정하면 우리는 PTE를 위해서만 4MB를 써야한다. 페이지가 4KB = 2^12이고, 2^32 / 2^12 -> 2^20인데, 주소 자체가 4B이므로 2^22 = 4MB가 필요. 매번 들고 있기에는 너무 부담스럽다.
- 그래서 시스템에서는 multi level page table을 사용.
  - 단순한 pte에서는 pte에서 virtual page -> physical page를 바로 매핑해지만, multi page에서는 page index가 다른 page table로 가게 해준다.
  - 이때 주목해야할 성질은, 한 pte에 속해있는 모든 vp가 unallocated일 경우 해당 pte는 null로 표현된다.
- 이게 왜 좋은가? "모든 page를 다 들고 있을 필요가 없도록"해주기 때문. null로 표현되는 pte는 들고 있을 필요가 없고, 우리는 필요한 pte만을 메인 메모리에 들고 있을 수 있다.

### 개념 정정

- pte(page table entry)는 `page table` 자료구조 자체가 아닌, vp의 상태를 추적하는 것으로 보아야 한다. 쉽게 표현하자면 하나의 vp에 대한 pp mapping으로 볼 수 있다. 단 unallocated인 경우도 있으므로, 해당 상황까지 고려한다면 한 vp에 대한 상태 추적으로 보는 것이 더 적절함.

### 통합 정리: end-to-end address translation

- TLB(translation lookaside buffer)이 왜 필요한지, 그리고 어떻게 동작하는지 살펴보자면,
  - VPN으로 "PTE/ PPN을 정석으로" 찾는 방법을 생각해보자. VPN이 있으면 대응하는 page table을 찾고, pte를 찾고 그때야 ppn을 찾을 수 있다. 너무 번거롭고 느림.
  - 그래서 tlb를 캐시로 사용한다. vpn을 key로 사용하는 형태다. vpn이 8비트이면 앞 6비트는 tag(TLBT)로 뒤 2비트는 set index(TLBI)로 사용한다.
  - 일반적인 캐시와 동일하게 사용되며, hit하면 PPN 정보를 획득한다. 이러한 이유로 PA를 쉽게 만들 수 있다 [PPN | VPO(=PP0)]
