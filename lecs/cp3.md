## x86-64의 기본. 
- 명령어들은 1-15 바이트로 표현될 수 있음. 
- .으로 시작하는 정보들은 일반적으로 어셈블러 / 링커를 위한 정보임. 

## Notation
- Immediate: $ 기호와 함께 그값을 직접 작성(주소가 아님!), 32비트까지만 표현가능. 
- R: 레지스터 안에서, 해당 주소에 있는 값을 가져옴 
- M: 메모리 안에서 해당 주소 안에 있는 값을 가져옴. 

## 이동 명령어 
- movb, movw, movl, movq 각각 1 / 2 / 4 / 8 바이트를 이동. 
- mov S D 꼴로 작성되고, S에 저장된 값을 D에 복사하는 방식임. 
  - S는 immediate / register / memory 모두 사용 가능. 
  - D는 register / memory 주소 중 하나.
  - 여기서 x86-64는 S / D 둘다 메모리 주소인 것은 mov에서 불가능함. 
- movabsq는 절대값을 복사함. 
- mov는 정해진 바이트만을 변경하지만, movl은 예외임. 
  - 이유? register에서 4byte를 변경하는 경우는 그 위의 higher order byte들에 0을 padding하기 때문. 
- S / D를 일종의 연산으로 생각해야. S는 읽기. D는 쓰기. 
  - 예제. %rax가 S에서는 rax에 저장된 "값"이지만, D에서는 "저장될 주소 자체"를 의미함


## 이동 명령어(작은 S에서, 큰 D로!)
- movz, movs. 여기서 z는 zero fill을 s는 sign fill을 수행. 
- 명령어는 각각 z는 5개, s는 6개(e.g., movzbw, movzbl, movzbq, movzwl, movzwq)
- movzlq는 왜 없는가? A. 컨벤션에 의해 4바이트 복사는 zero-fill을 자동으로 수행하므로(=movl과 동일한 동작)
- cltq -> SingExtend(%eax) -> %rax. 

## Push and Pop
- pushq S: R\[%rsp\] <- R\[%rsp\] - 8; M\[R\[%rsp\]\] <- S
  - 복잡해보이지만, 1) stack이 더 작을수록 top에 가깝다는 것, 2) 동작이 stack pointer(rsp)를 움직인 다음 그 자리에 S를 저장한다는 것을 유념하면 쉬움.
- popq D: D <- M\[R\[%rsp\]\]; R\[%rsp\] <- R\[%rsp\] + 8 
  - 마찬가지. 꺼내고, 포인터 이동시키고. 

## 3.5 logical & arithmetic operation
- leaq: mov의 specialized case. 메모리에서 레지스터로 이동시키는데 특화된 명령어. leaq S D가 D <- &S의 의미를 가짐. 
  - &S의 의미? "메모리 주소" 자체임. 예를 들자면, 다음과 같은 차이가 있다. 
  - movq 7(%rdx, %rdx, 4) %rax의 의미는? %rax = M\[5x + 7\] where %rdx = x. 
  - leaq 7(%rdx, %rdx, 4) %rax? %rax = 5x + 7 where %rdx = x. 다시 말하자면, 메모리에 저장된 값이 아닌, 메모리 주소 자체가 저장됨. 

- shift 연산
  - shift는 immediate를 이용하거나 cl 레지스터를 이용한 방식으로 사용할 수 있음.
    - 여기서 cl은 8바이트 레지스터지만 실제로는 quad(64 - 1)까지만 사용할 수 있고, 그 위 비트는 무시됨. 
    - 예: salq $cl, %rax가 있고, $cl에 65가 저장되어 있을 경우, 65 % 1 연산이 수행되어 rax를 1bit shift를 수행. 
  - 왼쪽 shift인 sal, shl은 동일한 연산을 수행한다. 이유는 부호를 고려할 필요 없기 때문. 
  - 반대로 오른쪽 shift인 sar, shr은 그 의미가 다르다. arithmetic shift이냐, logical shift냐의 차이. 

- Oct(128bit 연산)
  - 64 비트 레지스터에서는 계산하기 어려우므로, 두 레지스터에 저장하는 형태로 계산함.
  - imulq, mulq, cqto, idivq, divq로 구성되어있으며 하나의 인자(unary)만 받는 함수들임.  
    - i는 two's complement, i가 없으면 unsigned로 이해하면 됨.  
  - S 값을 받고 rax / rdx 레지스터를 사용하는 형태임. 
    - 곱셈의 경우: R\[%rdx\]:R\[%rax\] <- S * R\[%rax\]
    - 나눗셈의 경우: R\[%rdx\] <- R\[%rdx\]:R\[%rax\] mod S; R\[%rax\] <- R\[%rdx\]:R\[%rax\] / S; 

## 3.6 Control. 

### Condition codes 
- 조건 분기(e.g., c의 if, switch 등)를 레지스터에서 표현할 방법이 필요하다. 아래는 하나의 비트로 조건을 인코딩하는 방법들. 
  - carry out: 계산의 결과가 제한된 비트의 범위 바깥으로 나가는 경우(예: w비트 연산에서 계산의 결과가 2^w 이상인 경우)
- CF: carry flag, 바로 이전 연산에서 carry out이 발생했으면 1, 그렇지 않으면 0. 주로 unsigned 연산의 overflow를 판단하기 위해 사용.  
- ZF: zero flag. 가장 최근의 연산이 0을 만들었는가? 
- SF: Sign flag : 가장 최근 연산이 음수를 만들었는가?
- OF: overflow flag: 가장 최근 연산이 signed 관점에서 overflow를 만들었는가? 예컨대 덧셈을 가정하면, 부호가 동일한 두 개의 수를 계산했을 때 부호가 바뀌었는가? 

### Comparison and test 명령어들 
- mov, add 등 레지스터 변경을 해야만 condition code를 변경할 수 있는 명령어들과 다르게 cmp, test는 레지스터 변경 없이 condition code만 변경할 수 있음. 
- cmp: subtraction과 똑같음. b, w, l, q로 구성됨. 주의 사항은 뒤의 값으로부터 앞의 값을 뺀다는 것. cmpb S_1 S_2는 S_2 - S_1을 바이트 크기만큼 수행함. 
- test: and와 똑같음. 마찬가지로 b, w, l, q로 구성. 
- cmp / test 모두 destination의 레지스터 값을 변경시키지 않음. 

### Set 명령어들 
- condition code를 1바이트 레지스터 혹은 메모리에 넣는 연산을 수행. 
- 레지스터는 32bit / 64bit로 구성되므로 0 혹은 1인 1바이트 외 다른 공간(32bit일 경우 24, 64bit일 경우 56)은 모두 "클리어"해야함. 
- sete / setne, sets / setns, g / ge / l / le(signed), a / ae / b / be(unsigned)

### Jump 명령어 
- 순서대로 실행(sequential execution)하지 않고, 만나는 순간 실행 순서를 다른 방향으로 옮기는 것. 
- 직접 점프가 있고, 간접 점프가 있음.
  - 직접 점프: jmp 명령어 다음에 가야할 주소가 직접 등장(e.g., .L1). 이름은 어셈블러에서 지어준 것이고 실제로는 명령어 위치로부터 떨어진 위치(offset)를 표현
  - 간접 점프: jmp * 과 같은 형태로 표현되고, operand 주소에 저장된 주소로 이동함. 
- 이외에도 set과 동일하게, conditional codes의 비트정보를 확인하고 점프를 하는 명령어들이 있음(jmpe, ne, s, ns 등!)

### Jump를 인코딩하는 두 가지 방법. 
- PC-relative: pc(program counter)를 기반으로, 다음에 점프할 위치가 어딘지를 "상대주소"로 기록한다. 
  - jmp를 만났을 때, PC는 다음에 "실행할 명령어 주소"이고, 해당 주소를 기반으로, 점프할 지점이 얼마나 떨어져있는지만 작성해두면 됨. 
  - 예: jmp .L1; popq %eax와 같은 실행이 있을 경우, jmp에서 PC는 popq의 주소임(=다음 실행할 명령어의 주소!)
  - PC는 운영체제에서 언급하는 그 pc와 동일하며, 스레드마다 존재함. 
- 절대경로: jmp 뒤에 점프 위치를 4바이트로 구성된 절대경로로 작성함. 
- PC에 대한 조금 더 구체적인 설명. 
  - PC는 기본적으로 "현재 실행되고 있는 명령어의 주소"로서 %rip 레지스터에 저장됨. 
  - 명령어 실행이 끝나는 순간, "다음 명령어의 주소"로 rip가 갱신됨. 
  - 이러한 이유로 jmp의 실행이 끝나는 순간, rip는 다음 명령어 주소로 갱신되고, 이 시점을 기준으로 offset(PC-relative)가 계산됨.


### 브랜치를 다루는 두 가지 방법: Conditional Control Vs Conditional Move 
- Conditional Control: c의 goto 문법과 매우 유사한 형태. 
  - 먼저 조건문을 평가한다. 이때의 평가에 따라 전역변수(e.g., lt_cnt, ge_cnt)를 업데이트한다. 
  - 조건문에 기초해서 점프를 수행한다. if / else 분기에 따라 해야할 것이 블록으로 나누어져있다는 점에서 C 프로그래밍과 매우 유사함. 
- Conditional Move  
  - if / else 중 하나만 계산하는 것이 아니라, "둘 다 계산하고", 분기문을 가장 아래에 내린 다음, 둘 중 분기문에 맞는 값을 리턴하는 형태. 
  - "둘 다 계산하기 때문에 느릴 것"이다는 직관과 다르게, 현대 프로세서에서 더 빠른 경우들이 존재. 
    - 이유: conditional branch를 만나는 것 자체가 프로세서에게는 부담. 사전에 실행될 명령어들을 계산해두어야 빠른데, 분기문은 그걸 힘들게 함. 어떤 브랜치를 탈지 예측할 수 없기 때문. 
    - Q. 어찌됐든 최종적으로 분기문 쓰는 거 아님? A. No. 조건에 따라 다르게 리턴하는 cmovge를 보면 조건과 무관하게 cmovge를 쓰는 건 확정이고, 이게 실행의 마지막임. 

### Conditional Move 명령어
- 특정 조건에 따라 복사(mov)를 할 수도, 그렇지 않을 수도. 
  - 기본적인 형태: cmove S R. "조건을 만족하면 S에 저장된 값을 R에 저장"
  - 이때 S는 레지스터나 메모리에 존재해야함. 
- 문법은 set / jmp와 동일. e / ne, s / ns 등으로 구성

### Loops
- 기계 레벨 명령어에는 명시적인 loop(e.g., while / for) 명령어가 존재하지 않음. 단, jmp와 test를 통해 표현. 크게 두 가지 방법론이 있음.
- 1. do-while style
  - 초기화 코드; loop 진입점 -> body 구문 실행 -> 분기 조건 확인 -> 조건이 맞을 경우 진입점으로 되돌아 감 -> 아닐 경우 리턴. 
  - loop .L2 -> body stmt -> test -> return rax
- 2. while style.
  - 크게 두 가지 방법론이 존재함. jump-to-middle / guarded do. 
  - jump-to-middle: 두 개의 call site(.L2, .L3)가 순서대로 있을 때, 조건식을 계산한 뒤, .L3로 바로 이동, 조건식을 만족하지 않으면 리턴하고 만족하면 L2로 이동. L2가 반복구문, L3가 exit으로 생각할 수 ㅣ있음
  - guarded-to: do-while과 유사함. call site가 두 개(.L2, .L3) 있음. do-while가 동일하게 첫 번째로 조건식을 계산함. if를 통해 계산하고 조건식을 만족하지 않으면 L3로 이동함. L3는 done으로 반복의 종료임. 조건식을 만족하면 L2로 "순서대로 이동하며 실행함(=명령어 점프 없음)" 

### Switch
- jump table(이하 jt)을 통해 수행되며 어셈블리에는 각 케이스마다 대응되는 블럭들이 존재함. 얘를 들어 case 1:의 경우 .L1과 같이 대응되는 파트가 생성. 
- fall through(=c의 switch 구문에서 case에 break 를 작성하지 않아 다음 case로 흘러들어가는 경우)를 고려해서 작성해야.

## 3.7 Procedures

### Basics. 
- 알고 싶은 것: 함수 두 개(e.g., P, Q)가 존재할 때 특정 함수(P)가 다른 함수(Q)를 호출할 경우, 레지스터에서 어떻게 다루는지. 
- 한 함수(이하, procedures)가 실행될 때 필요한 요소(e.g., 인자, 로컬 변수)는 스택에 저장되며 이를 스택 프레임이라고 지칭한다. 
- 함수(P)에서 다른 함수(Q)를 호출하는 경우, Q가 종료되었을 때 돌아갈 주소인 P의 시작지점이 필요하다. 이러한 이유로, 
  - 함수 호출을 만날 경우, 현재 함수(P)의 주소를 적어둔다. 이때 해당 주소는 호출되는 함수가 아닌 호출하는 함수의 스택프레임으로 포함된다. 
  - Q가 실행되고 ret(리턴, 종료) 명령어를 만날 경우, 적어둔 P 주소로 돌아간다. 

### Passing Values. 
- 인자값으로, 6개까지는 정해진 레지스터(rdi, rsi, rdx, rcx, r8, r9)에 들어가고, 이후로는 스택에 저장됨.  
- 리턴값은 rax에 저장되어 사용 가능. 

### 지역 변수(Local Variable) 
- 지역변수는 stack frame에 저장된다. 이유는 크게 세 가지가 존재. 
  - 레지스터가 모두 들고 있기엔 너무 많을 수도. 
  - array / struct 같은 복잡한 형태일 수도. 
  - 주소 연산자 &를 통해 계산되어 메모리 사용이 강제될 수도. 
- 위와 같은 수요로 인해, 필요시 rsp 값을 줄어들도록(decrementing) 만들어, 스택공간을 확보함. 
  - 모든 계산이 끝나면 다시 더함으로써(incrementing) 다시 메모리를 확보. 


### Callee-saved 
- x86은 함수가 상호작용 하는 경우를 고려해서 설계되었음. 통상 caller-callee로 구분. 
- 해당 상황을 고려하면 callee가 실행될 때 들고 있는 레지스터 중 caller의 추후 실행을 위해 반드시 보존되어야 하는 것들이 존재하고 이것을 callee-saved로 칭함. 
  - 여기서 "보존"은 callee-saved가 callee의 실행 전 / 후로 다른 게 없다는 것을 의미함. 다시 말해, 변경해도 원래대로 복구할 수만 있다면 ok. 
  - 구체적으로는 rbx, rbp, r12-r15가 여기에 해당함. 
- call-saved는 두 가지 방법으로 보존 가능. 1)레지스터를 전혀 건드리지 않기, 2)임시로 레지스터 값을 스택에 푸쉬해두고, 복구시 스택 값을 팝하기. 
  - 2에서 푸쉬하는 경우 이를 "saved register"라고 말함. 

### Caller-saved 
- caller가 저장해야할 값이므로, callee 입장에서는 임의로 변경해도 됨. 
- callee-saved와 rsp를 제외한 모든 레지스터가 해당. 

## 3.8 Array allocation and access

### 배열(Array)의 성질 
- T x[\n\] 형태로 선언될 경우, 
  - T 데이터 타입의 크기 * 원소의 수(n)만큼의 용량을 가지게 되고, 
  - x 자체가 데이터의 시작 주소가 되며, 
  - n은 [0, n-1]의 범위를 가지게 된다. 
- x86-64의 문법을 고려하면, 임의의 배열 원소에 쉽게 접근하도록 설계된 걸 알 수 있음(e.g., movl (%rdx,%rcx,4),%eax)

### 포인터 계산
- 예를 들어 int *p와 같은 선언이 있고, p가 1000이라는 메모리 주소를 가리킨다고 하자. 이때, 
  - p + 3은 1000 + (4 * 3)과 같이 계산된다. 여기서 4는 int의 크기(4바이트)를 의미한다.  
  - 일반화하자면, 주소 + (자료형의 크기 * 더해지는 값) 형태로 계산된다. 


## 3.9 Data Structures. struct / union 

### Structures
- 여러개의 오브젝트를 하나의 구조(structure)에 묶어두고, 하나의 이름으로 부르기 위한 개념. 
- 구조체의 포인터는 배열과 유사. 가장 앞에 있는 원소의 주소. 
- 그리고 각 공간은 자료형 크기마다 offset으로 구분되어 있음. 

### Unions
- 일종의 합타입 표현. 구조체가 선언되는 모든 멤버변수들을 들고 있다면, 공용체는 그중 하나만 들고 있음. 
- 이러한 이유로 공용체는 가장 큰 용량을 가진 멤버의 용량이 공용체의 용량이 됨. 
- 저장된 바이트를 "어떻게 읽을 것인가"로 결정됨

### Data Alignment
- 프로세서들을 통상 특정한 바이트수 K(e.g., 2, 4, 8)를 통해 데이터를 접근하므로, K 배수에 얻고자 하는 데이터가 존재하는 게 좋음. 
  - 8바이트 데이터가 0-7에 존재하는 것과 2-9에 존재하는 것은 다른 데이터 효율을 가짐. 전자는 한 번에 볼 수 있지만, 후자는 두 번에 나누어(0-7, 8-15) 보아야. 
- 이런 이유로 align 명령어가 존재함. 메모리 접근을 용이하게 하도록 하는 것이 목적. .align 8은 "다음 명령어는 8의 배수 메모리 주소에 위치시킬 것"이라는 의미. 
- 그 외에도, 데이터가 K 배수 안에 존재하지 않을 경우, 의도적으로 데이터에 패딩을 넣는 경우가 있음. 
  - 구조체의 멤버가 하나의 char와 두개의 int로 구성되어 있을 경우 9바이트를 가지지만, K값을 고려하여 패딩을 추가하는 경우가 존재함. 예를 들어 k가 4일 경우, 해당 구조체의 뒤에 3바이트를 붙여 12바이트로 만들수도.
